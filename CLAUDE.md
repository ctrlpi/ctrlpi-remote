# CLAUDE.md - ctrlpi-remote

This file provides guidance to Claude Code when working in this repository.

## What this is

A zero-dependency stdio MCP server (`ctrlpi-remote.js`, Node 20+) that forwards to the `ctrlpi-mcp`, `pico-bay` and `pi-bay` servers running in HTTP mode on other machines: all three, or the one named by the first argument. The `ctrlpi-remote` plugin in `claude-plugins` runs it with no argument. The npm package is **`ctrlpi-remote`** (unscoped), executable `ctrlpi-remote.js`. The `files` allowlist in `package.json` ships only `ctrlpi-remote.js` (plus npm's own README, LICENSE and package.json), so this file never ships; re-check with `npm pack --dry-run` after touching it.

It lives at `ctrlpi-remote/` in the ctrlpi workspace, its own git repository (the root gitignores it). The root `CLAUDE.md` rules apply here. Publishing is described in the root `CLAUDE.md` only.

## Design

- **Targets** (`TARGETS`): default port, tool name `prefix` (`mcp_`, `pico_`, `pi_`), the list tool that fans out, the UI tool, and `single` (ctrlpi-mcp: only the first server found is used, since two would drive the same agents). `enabledTargets()`: the one on the command line, else `"targets"` in `remote-config.json` (a list of names), else all three.
- **Config**: `~/.ctrlpi/remote-config.json` (`--config` folder or `.json` path, `resolveConfigFile()`), a list per target of `{ip, port, api_key, key_set, updated_at}`, plus the optional `targets` list. A write (`saveServers()`) replaces only its own target's list, atomically, mode `0600`. No `--key` flag, ever: keys live only in the file.
- **`resolveServers()`** (once per target, in parallel, each with its own sweep of its port): `--host` uses that address only (on each target's port; `--port` needs a target). Otherwise every saved address is checked with `GET /hello`; when nothing is saved, a saved address is dead, or `force` (`remote_rescan`) asks, `sweep()` searches the /24 (`localIp()`: UDP socket to `8.8.8.8:80`, then the interfaces). A found server on the default key is claimed (`claim()`: the key is saved first, sent with a ping, and removed again if refused). A found server already claimed is tried only with the keys of dead entries (a moved server); that is the rule that a saved key goes to a new address only once the old one is dead. A server on the default key is never sent a key it would claim by accident.
- **The proxy answers some messages itself** (`createProxy()`): `initialize` (at once, before any search: `serverInfo` `ctrlpi-remote`, `tools.listChanged: true`, the client's version when it is one of `LEGACY_PROTOCOLS`, else the newest), `ping`, and `-32601` for every other method but `tools/list` and `tools/call` (`server/discover` included, so a client uses the older revisions). Each server gets the client's own `initialize` the first time it is used (`ensureInit()`), and its own session; client notifications go to every server already initialized.
- **Searches** (`scan()`): one at start, and one per `remote_rescan` (forced, after the start-up one); `tools/list` and `tools/call` wait for the first. There is no timer: most users run one or two of the three servers, and a timed search would sweep the LAN for the others forever. A server still in use keeps its session. When the servers in use change after the first search, the client gets `notifications/tools/list_changed`. Problems are logged only when they change.
- **Built-in tools**: `remote_servers_list` (per target: servers in use and problems: already claimed, does not answer, rejected the key, MCP switched off, turned off by `targets`) and `remote_rescan` (a forced search of every target, then the same report).
- **Tools**: `tools/list` is each target's tools (only names with its prefix) from its first live server, then the built-in tools; a target that fails (wrong key) adds none, and its error shows in `remote_servers_list`. `tools/call` picks the target by prefix.
- **Forwarding** (`post()`): `POST /mcp` with `Api-Key`, `Mcp-Session-Id`, and `protocolHeaders()` (on the current revision `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` from the body, as pico-bay and pi-bay check; otherwise the negotiated version). `202` writes nothing; `403` is a key error; `404` with a JSON-RPC body is passed on, without one it re-initializes once, then reports "MCP is switched off". Only the connection has a timeout (`CONNECT_TIMEOUT_MS`), never the answer. stdin closing waits for the requests already sent.
- **Several servers of one target**: its tools get a `host` enum (required except on the list tool); `tools/call` routes by `host`, or fans the list tool out and merges the results by host. A server that stops answering `/hello` drops out of the enum.
- No servers: the proxy still starts, lists the built-in tools, and answers a call to a missing target with the reason and a hint (`RESCAN_HINT`): start the server with its HTTP MCP on, then call `remote_rescan`. `remote_servers_list` and `remote_rescan` add a `message` saying the same when no server of any target is connected.
- **UI tools** (`pico_ui`, `pi_ui`): forwarded like any tool, so they run on the remote bay. A remote request is never a local desktop, so the bay does not open a browser: the result is `opened: false` and a `url` built from the request's `Host` (checked against a real `pico-bay` and `pi-bay` on b4.local: `http://b4.local:7426` and `:3141`). `openUiLocally()` then opens that URL here (`open`, `xdg-open`, `cmd /c start`; `CTRLPI_REMOTE_BROWSER` in tests) and returns `{url, opened: true}`, but only when the URL is `http://` on the address and port of the server that answered, and only on a desktop session (`localDesktop()`: no `SSH_CONNECTION`, and on Linux a `DISPLAY` or `WAYLAND_DISPLAY`); otherwise the result is passed on and the user opens the URL themselves. It works only when the bay listens on a reachable address (`--host 0.0.0.0`, or the Pi default; `pico-bay` and `pi-bay` bind to `127.0.0.1` otherwise), and the web UI has no key, so `--host 0.0.0.0` exposes it to the LAN. With `--ui off` the tool refuses with a tool error. `ctrlpi-mcp` has no UI tool.
- `--rotate-keys`: `POST /remote-config` with a new key per server of every target served, saved on `200`, then exit.

## Tests

`npm test` runs `test/ctrlpi-remote.test.js`: fake servers in the test process (never `spawnSync` the proxy there, it would block them), with `CTRLPI_REMOTE_SCAN_LAN=0` and `CTRLPI_REMOTE_SCAN_PORTS` keeping every search on `127.0.0.1`. When the workspace has them next to this folder, it also runs against the real `ctrlpi-mcp --http` (subprocess) and `pico-bay` / `pi-bay` (in process, `HOME` moved, only `initialize` and `tools/list`, so no board or SSH device is touched).
